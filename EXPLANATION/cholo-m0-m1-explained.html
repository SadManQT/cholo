তুমি এখন পর্যন্ত ঠিক কী বানিয়েছ?

এই পেজটা তোমার নিজের cholo রিপোর ভেতরের আসল ফাইল থেকে বানানো — কোনো কাল্পনিক উদাহরণ না। প্রতিটা কোড ব্লক তোমার প্রজেক্টে সত্যিই আছে। লক্ষ্য একটাই: প্রতিটা লাইন কেন লেখা হয়েছে, আর তার সিনট্যাক্সটা আসলে কী বোঝায় — দুটোই একসাথে বোঝা।

ভাষা মিশ্রিত থাকবে ইচ্ছা করেই — ব্যাখ্যা বাংলায়, কোড আর টেকনিক্যাল টার্ম ইংরেজিতে (যেমন বেশিরভাগ বাংলাদেশি ডেভেলপার শেখে)। কোড কখনো অনুবাদ হয় না, কম্পিউটার শুধু ইংরেজি সিনট্যাক্সই বোঝে।

M0 Git + repo-র বেসিক ফাইলগুলো

যেকোনো প্রজেক্টের প্রথম কাজ হলো version control (Git) চালু করা, আর কিছু নিয়ম-কানুন ফাইল রাখা যাতে secret কখনো ভুলে commit না হয়।

.gitignoreকোন ফাইল Git ট্র্যাক করবে না
# secrets — never commit
.env
.env.local

# dependencies
node_modules/

# build output
dist/
build/

# coverage
coverage/

# OS cruft
.DS_Store
সিনট্যাক্স নোট .gitignore একটা প্লেইন টেক্সট ফাইল, প্রতি লাইনে একটা প্যাটার্ন। node_modules/ এর শেষে / মানে এটা একটা ফোল্ডার। # দিয়ে শুরু মানে কমেন্ট — Git এটা উপেক্ষা করে। এই ফাইল ছাড়া node_modules (হাজার হাজার ফাইল!) আর তোমার .env (পাসওয়ার্ড সহ) দুটোই Git-এ চলে যেত।
.env.exampleসব environment variable-এর টেমপ্লেট, ভুয়া মান দিয়ে
# Copy this file to .env and fill in real values. .env is git-ignored —
# never commit it (doc 07 §2).

# --- Postgres (read by docker-compose.yml) ---
POSTGRES_USER=cholo
POSTGRES_PASSWORD=change-me
POSTGRES_DB=cholo

# --- Backend (read later by server/config/env.js, doc 08 §5) ---

কেন দুটো ফাইল — .env আর .env.example? .env আসল secret রাখে আর Git থেকে লুকানো থাকে (.gitignore-এ আছে দেখেছ)। .env.example Git-এ থাকে, যাতে অন্য কেউ (বা তুমি নিজেই ৬ মাস পর) জানতে পারে ঠিক কোন কোন variable দরকার — শুধু আসল মানগুলো ছাড়া। README.md-তেই দেখবে প্রথম quickstart command হলো cp .env.example .env।

M0 Environment Variable আসলে কী?

Environment variable হলো key=value জোড়া যা তোমার অ্যাপের বাইরে থেকে দেওয়া হয় — কোডে hardcode করা হয় না। এতে সুবিধা: একই কোড dev-এ এক config নিয়ে চলে, production-এ আরেক config নিয়ে — কোড পাল্টাতে হয় না, শুধু .env পাল্টালেই হয়।

Variableব্যবহার
POSTGRES_USER/PASSWORD/DB/PORTdocker-compose.yml পড়ে Postgres container বানায়
DATABASE_URLExpress অ্যাপ এই একটা URL দিয়ে Postgres-এ কানেক্ট করে (উপরের ৪টার সমন্বয়ে বানানো)
NODE_ENVঅ্যাপ কি development/test/production মোডে চলছে বোঝায়
CLIENT_ORIGINCORS-এর জন্য — কোন frontend URL থেকে request নেওয়া নিরাপদ

M0 docker-compose.yml — PostgreSQL চালু করা

Docker তোমার কম্পিউটারে সরাসরি PostgreSQL ইনস্টল না করেই একটা "কন্টেইনার"-এ (isolated mini-machine) PostgreSQL চালায়। এতে সবার মেশিনে একই ভার্সন, একই ব্যবহার নিশ্চিত হয় — "works on my machine" সমস্যা এড়ানো যায়।

docker-compose.ymlYAML ফরম্যাট
services:
  postgres:
    image: postgres:16
    restart: unless-stopped
    environment:
      POSTGRES_USER: ${POSTGRES_USER}
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD}
      POSTGRES_DB: ${POSTGRES_DB}
    ports:
      - "${POSTGRES_PORT:-5433}:5432"
    volumes:
      # named volume: the actual data directory, survives `docker compose down`
      - cholo_pgdata:/var/lib/postgresql/data
      # bind mount: runs once against an EMPTY data dir (first boot only).
      - ./database/schema.sql:/docker-entrypoint-initdb.d/01-schema.sql:ro
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U ${POSTGRES_USER} -d ${POSTGRES_DB}"]
      interval: 5s
      timeout: 5s
      retries: 10

volumes:
  cholo_pgdata:

লাইন ধরে ধরে — YAML সিনট্যাক্স

অংশমানে
services:YAML-এ indentation (স্পেস) দিয়ে nesting বোঝানো হয় — {} ব্র্যাকেট লাগে না। services এর নিচে যা কিছু দুই স্পেস ইন্ডেন্ট করা, সব ঐ services-এর অংশ।
image: postgres:16Docker Hub থেকে অফিসিয়াল postgres ইমেজ, ভার্সন 16 ব্যবহার করবে।
${POSTGRES_USER}docker-compose .env ফাইল থেকে automatically এই ভ্যারিয়েবলটা বসিয়ে দেয়। এভাবে পাসওয়ার্ড ফাইলে hardcode করতে হয় না।
"${POSTGRES_PORT:-5433}:5432"ফরম্যাট host:container। :-5433 মানে "যদি POSTGRES_PORT সেট করা না থাকে, ডিফল্ট 5433 ব্যবহার করো"। container-এর ভেতরে Postgres সবসময় 5432-তেই চলে, কিন্তু বাইরে থেকে (তোমার মেশিন থেকে) 5433 দিয়ে অ্যাক্সেস করবে।
volumes (দুই ধরনের)Named volume (cholo_pgdata:...) — আসল ডেটা এখানে জমা থাকে, container বন্ধ করলেও হারায় না। Bind mount (./database/schema.sql:...) — তোমার লোকাল ফাইল container-এর ভেতরে একটা path-এ mount হয়; :ro মানে read-only।
healthcheckDocker কে বলে দেয় কীভাবে বুঝবে Postgres আসলে রেডি কিনা — শুধু "chalu হয়েছে" না, "connection নেওয়ার মত প্রস্তুত" কিনা। pg_isready কমান্ড প্রতি ৫ সেকেন্ডে চেক করে, ১০ বার চেষ্টা করে।
schema.sql শুধু প্রথমবারই লোড হয় কেন? Postgres-এর অফিসিয়াল ইমেজ এই আচরণ নিয়েই বানানো: /docker-entrypoint-initdb.d/ ফোল্ডারে থাকা .sql ফাইল শুধু তখনই চলে যখন ডেটা ডিরেক্টরি একদম খালি থাকে (একদম প্রথমবার)। এজন্যই schema.sql পাল্টালে docker compose down -v (volume সহ মুছে ফেলা) করে আবার up করতে হয়, নাহলে পরিবর্তন ধরবে না।

M0 database/schema.sql — এক ঝলক

পুরো স্কিমাতে ৫৪টা টেবিল আছে (docs 01-04 এ পুরো ডিজাইন)। M0/M1-এ আমরা শুধু এর সবচেয়ে সহজ টেবিলটা — cities — ব্যবহার করেছি প্রথম feature বানাতে।

database/schema.sql (অংশ)
CREATE TABLE cities (
    id          SMALLINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    name        VARCHAR(60) NOT NULL UNIQUE,
    country     VARCHAR(60) NOT NULL DEFAULT 'Bangladesh',
    timezone    VARCHAR(40) NOT NULL DEFAULT 'Asia/Dhaka',
    currency    CHAR(3) NOT NULL DEFAULT 'BDT',
    is_active   BOOLEAN NOT NULL DEFAULT true,
    launched_at DATE
);
SQL অংশমানে
GENERATED ALWAYS AS IDENTITYPostgreSQL নিজে থেকে auto-increment id বানায় (1, 2, 3...)। ম্যানুয়ালি id দেওয়ার দরকার নেই।
PRIMARY KEYএই কলাম দিয়ে প্রতিটা row uniquely চেনা যায়; ডাটাবেজ ইনডেক্স করে দ্রুত খোঁজার জন্য।
NOT NULLএই কলাম খালি রাখা যাবে না — ডাটাবেজ লেভেলেই এটা জোর করে, শুধু কোড-লেভেলে না।
UNIQUEএকই মান দুইবার থাকতে পারবে না (দুইটা শহরের নাম একই হতে পারবে না)।
DEFAULT 'Bangladesh'যদি ইনসার্টের সময় মান না দেওয়া হয়, এই ডিফল্ট মান বসে যাবে।
কেন এত কড়া নিয়ম ডাটাবেজেই? AGENTS.md-এর কনভেনশন অনুযায়ী — business invariant গুলো constraint (CHECK/UNIQUE/FK) দিয়ে বসানো হয়, শুধু অ্যাপের কোডে না। কারণ অ্যাপের কোডে বাগ থাকতে পারে, কিন্তু ডাটাবেজ কনস্ট্রেইন্ট কখনো ভুল ডেটা ঢুকতে দেবে না — এটাই "defense in depth"।

M1 src/app.js — Express অ্যাপের কেন্দ্র

এই ফাইলে Express অ্যাপ বানানো হয় আর তার মধ্যে middleware (মাঝে বসে থাকা ফাংশনগুলো) একটার পর একটা যুক্ত করা হয়। এটাকে বলা যায় request-এর "প্রসেসিং লাইন"।

_request (underscore দিয়ে শুরু)কনভেনশন — এই প্যারামিটারটা ব্যবহার হচ্ছে না, কিন্তু Express-এর সিগনেচার অনুযায়ী জায়গায় থাকতেই হবে (এরপর response আসবে)। underscore দিয়ে বোঝানো হয় "ইচ্ছাকৃতভাবে ব্যবহার করা হয়নি"।
app.use('/api/v1', apiRouter)এই path prefix দিয়ে শুরু হওয়া সব request apiRouter-এ পাঠিয়ে দেয় — এটা "mounting" একটা sub-router।
app.use(notFound)উপরের কোনো route যদি না মেলে, এই পর্যন্ত request পৌঁছে যায় — মানে ৪০৪।

async/await + try/catch — কেন একসাথে? checkDatabaseConnection() একটা Promise রিটার্ন করে (কারণ ডাটাবেজে কানেক্ট করতে সময় লাগে, এটা instant না)। await মানে "এই Promise শেষ না হওয়া পর্যন্ত এখানে থামো, তারপর result নিয়ে এগোও" — এটা ছাড়া তুমি একটা "pending" promise পেতে, আসল ডেটা না। await শুধু async ফাংশনের ভেতরেই ব্যবহার করা যায়। আর Promise reject (fail) হলে সেটা ধরার জন্য try/catch — এখানে ডাটাবেজ কানেকশন ফেইল করলে ক্যাচ ব্লকে গিয়ে ৫০৩ status পাঠানো হচ্ছে, অ্যাপ ক্র্যাশ করছে না।

M1 src/server.js — সার্ভার চালু আর গ্রেসফুল শাটডাউন

app.js শুধু অ্যাপটা বানায়server.js সেটাকে আসলে চালু করে (listen করে) আর বন্ধ হওয়ার সময়টাও পরিষ্কারভাবে সামলায়।

server/src/server.js
import app from './app.js';
import { pool } from './config/db.js';
import { env } from './config/env.js';

const server = app.listen(env.PORT, () => {
  console.log(`Cholo API listening on port ${env.PORT}`);
});

let isShuttingDown = false;

function shutdown(signal) {
  if (isShuttingDown) return;
  isShuttingDown = true;

  console.log(`${signal} received; shutting down HTTP server`);
  server.close(async (error) => {
    if (error) {
      console.error('HTTP server shutdown failed:', error);
      process.exitCode = 1;
    }

    await pool.end();
  });
}

process.on('SIGINT', () => shutdown('SIGINT'));
process.on('SIGTERM', () => shutdown('SIGTERM'));
অংশব্যাখ্যা
app.listen(env.PORT, callback)এখন থেকে OS-এর নির্দিষ্ট port-এ (যেমন 3000) আসা HTTP request গুলো এই অ্যাপ শুনবে (listen করবে)। callback একবারই চলে, যখন সার্ভার আসলে চালু হয়ে যায়।
Template literal `Cholo API listening on port ${env.PORT}`ব্যাকটিক (`) দিয়ে স্ট্রিং লিখলে ভেতরে ${...} দিয়ে সরাসরি ভ্যারিয়েবল বসানো যায় — পুরনো 'text ' + variable + ' text' এর চেয়ে পরিষ্কার।
let isShuttingDown = false;let এমন ভ্যারিয়েবলের জন্য যেটার মান পরে বদলাবে (এখানে true হয়ে যাবে)। এর বিপরীতে const — একবার সেট হলে আর বদলানো যায় না।
process.on('SIGINT', ...)SIGINT আর SIGTERM হলো OS-এর পাঠানো সিগন্যাল যখন কেউ Ctrl+C চাপে বা Docker/hosting platform অ্যাপ বন্ধ করতে চায়। এগুলো না ধরলে অ্যাপ হঠাৎ মাঝপথে বন্ধ হয়ে যেত, ডাটাবেজ কানেকশনও অগোছালোভাবে বন্ধ হতো।
server.close(callback)নতুন কোনো request আর নেওয়া হবে না, কিন্তু চলমান request গুলো শেষ হতে দেওয়া হয় — তারপর callback চলে।
await pool.end()ডাটাবেজ connection pool-এর সব কানেকশন ঠিকভাবে বন্ধ করে — আকস্মিকভাবে কেটে দেওয়া না।
isShuttingDown ফ্ল্যাগ কেন? SIGINT আর SIGTERM দুটোই একসাথে বা বারবার আসতে পারে। এই ফ্ল্যাগ ছাড়া shutdown() দুইবার চলতে পারত, আর server.close() দুইবার ডাকলে সমস্যা হতে পারে। এটা একটা সাধারণ "idempotency guard" প্যাটার্ন — একই কাজ দুইবার নিরাপদে না চালানোর কৌশল।

M1 config/env.js — fail-fast validation

এই ফাইলটার কাজ: .env ফাইল পড়া, আর যাচাই করা যে দরকারি সব ভ্যারিয়েবল ঠিকভাবে দেওয়া আছে কিনা। কিছু ভুল/অনুপস্থিত থাকলে অ্যাপ চালুই হবে না — চুপচাপ ভুল মান নিয়ে চলবে না।

server/src/config/env.js
import { dirname, resolve } from 'node:path';
import { fileURLToPath } from 'node:url';

import dotenv from 'dotenv';
import { z } from 'zod';

const currentDirectory = dirname(fileURLToPath(import.meta.url));
const rootEnvPath = resolve(currentDirectory, '../../../.env');

dotenv.config({ path: rootEnvPath, quiet: true });

const envSchema = z.object({
  NODE_ENV: z.enum(['development', 'test', 'production']).default('development'),
  PORT: z.coerce.number().int().positive().max(65_535).default(3000),
  DATABASE_URL: z.string().min(1, 'DATABASE_URL is required').url('DATABASE_URL must be a valid URL'),
  CLIENT_ORIGIN: z.string().url('CLIENT_ORIGIN must be a valid URL').default('http://localhost:5173'),
});

function formatIssues(issues) {
  return issues
    .map((issue) => `  - ${issue.path.join('.') || 'environment'}: ${issue.message}`)
    .join('\n');
}

function loadEnvironment(source) {
  const result = envSchema.safeParse(source);

  if (!result.success) {
    throw new Error(`Invalid environment configuration:\n${formatIssues(result.error.issues)}`);
  }

  return Object.freeze(result.data);
}

export const env = loadEnvironment(process.env);

সিনট্যাক্সব্যাখ্যা
import.meta.urlESM মডিউলে বর্তমান ফাইলের নিজের URL/path পাওয়ার উপায় (পুরনো CommonJS-এর __dirname-এর বদলি)।
fileURLToPath() + dirname()URL কে সাধারণ ফাইল path-এ বদলে, তারপর সেটার ফোল্ডার বের করে — যাতে .env ফাইলের সঠিক লোকেশন বের করা যায়, তুমি কোথা থেকে script চালাচ্ছ তার উপর নির্ভর না করে।
resolve(currentDirectory, '../../../.env')relative path থেকে absolute path বানায়। তিনটা ../ মানে তিন ধাপ উপরে উঠে root ফোল্ডারের .env খোঁজা (config/ → src/ → server/ → root)।
z.object({...})Zod লাইব্রেরি দিয়ে একটা "শেপ" (schema) সংজ্ঞায়িত করা হচ্ছে — এই অবজেক্টের কোন key-তে কী ধরনের মান থাকা বাধ্যতামূলক। এটাকে "runtime validation" বলে — TypeScript-এর টাইপের মতো, কিন্তু আসল রানটাইমেও চেক করে।
z.enum([...])মান অবশ্যই এই তালিকার একটা হতে হবে, নাহলে ভুল।
z.coerce.number().env ফাইলে সব মান স্ট্রিং হিসেবে আসে (যেমন "3000") — coerce সেটাকে জোর করে নাম্বারে রূপান্তর করে যাচাই করার আগে।
মেথড চেইনিং .int().positive().max(65_535)প্রতিটা মেথড আরেকটা নতুন validator রিটার্ন করে, তাই একের পর এক জোড়া লাগানো যায় — পড়তে প্রায় ইংরেজি বাক্যের মতো লাগে: "নাম্বার, ইন্টিজার, পজিটিভ, সর্বোচ্চ ৬৫৫৩৫"।
65_535আন্ডারস্কোর সংখ্যার মাঝে শুধু পড়তে সুবিধার জন্য (numeric separator) — 65535-এর মতোই কাজ করে, শুধু চোখে সহজে বড় সংখ্যা বোঝা যায়।
safeParse()Zod-এর দুই ধরনের parse আছে: parse() ভুল হলে সরাসরি throw করে, safeParse() একটা { success, data বা error } অবজেক্ট রিটার্ন করে — তুমি নিজে ঠিক করো কী করবে।
result.error.issues.map(...).map() একটা অ্যারের প্রতিটা আইটেমকে আরেকটা ফর্মে রূপান্তর করে নতুন অ্যারে বানায় — এখানে প্রতিটা ভ্যালিডেশন-এরর অবজেক্টকে একটা readable স্ট্রিং লাইনে বদলানো হচ্ছে।
throw new Error(...)ইচ্ছাকৃতভাবে একটা এরর তৈরি করে "ছুড়ে" দেওয়া হচ্ছে — এটা এই ফাংশনের normal flow থামিয়ে দেয়, আর কেউ না ধরলে পুরো প্রোগ্রাম ক্র্যাশ করে। এখানেই ইচ্ছাকৃত: ভুল env নিয়ে চালানোর চেয়ে অ্যাপ বুট হওয়ার আগেই ক্র্যাশ করা ভালো।
Object.freeze(result.data)এই অবজেক্টের কোনো property যেন পরে ভুলবশত পাল্টানো না যায় সেটা নিশ্চিত করে — env একবার লোড হলে, immutable (অপরিবর্তনীয়) থাকা উচিত।
কেন module লোড হওয়ার সাথে সাথেই validate করা হয় (top-level এ, ফাংশনের ভেতরে না)? লক্ষ্য করবে export const env = loadEnvironment(process.env); — এটা ফাইলের একদম নিচে, কোনো ফাংশনের ভেতরে না। মানে এই ফাইল প্রথমবার ইম্পোর্ট হওয়ার সময়ই এটা চলে। এইজন্য server.js-এ import { env } from './config/env.js' লেখা মাত্রই — অ্যাপ চালুর একদম শুরুতেই — env ভুল থাকলে ক্র্যাশ করবে, কোনো request আসার আগেই। এটাই "fail-fast" — docs/08 §10-তে বলা "৩টার সময় missing-env crash" এড়ানোর কৌশল।

Middleware হলো এমন একটা ফাংশন যেটা request আর response-এর মাঝে বসে, আর next() ডেকে পরবর্তী ধাপে যায় (অথবা আটকে দেয়)। Express-এ প্রতিটা middleware-এর সিগনেচার হয় (request, response, next) — আর error-handling middleware-এর হয় বিশেষভাবে ৪টা প্যারামিটার: (error, request, response, next)।

errorHandler.js — সবকিছুর কেন্দ্রীয় এরর হ্যান্ডলার

server/src/middlewares/errorHandler.js
import { AppError } from '../utils/AppError.js';
import { ERROR_MESSAGES } from '../utils/errorMessages.js';
import { logger } from '../utils/logger.js';

const postgresErrors = Object.freeze({
  23505: { status: 409, code: 'DUPLICATE' },
  23503: { status: 422, code: 'VALIDATION_FAILED' },
  23514: { status: 422, code: 'VALIDATION_FAILED' },
});

function sendError(response, status, code, details) {
  const error = {
    code,
    message: ERROR_MESSAGES[code] ?? code,
  };

  if (details !== undefined) {
    error.details = details;
  }

  return response.status(status).json({ success: false, error });
}

export function errorHandler(error, request, response, next) {
  if (response.headersSent) {
    return next(error);
  }

  if (error instanceof AppError) {
    return sendError(response, error.status, error.code, error.details);
  }

  if (error.type === 'entity.parse.failed') {
    return sendError(response, 422, 'VALIDATION_FAILED', [
      { field: 'body', issue: 'Request body must contain valid JSON.' },
    ]);
  }

  const postgresError = postgresErrors[error.code];

  if (postgresError) {
    return sendError(response, postgresError.status, postgresError.code);
  }

  logger.error('Unhandled request error', error, {
    method: request.method,
    path: request.originalUrl,
  });

  return sendError(response, 500, 'INTERNAL');
}

৪-প্যারামিটার ফাংশন (error, request, response, next)Express বিশেষভাবে চিনে নেয় — ঠিক ৪টা প্যারামিটার থাকলেই এটাকে error-handling middleware ধরে নেয় (৩টা হলে সাধারণ middleware ধরত)। কোনো জায়গায় next(someError) ডাকা হলে Express সরাসরি এখানে চলে আসে, মাঝের সব সাধারণ middleware বাদ দিয়ে।

error instanceof AppErrorচেক করছে এই error অবজেক্টটা আমাদের নিজেদের বানানো AppError ক্লাসের (নিচে দেখো) instance কিনা — মানে এটা কি একটা "আমরা প্রত্যাশা করা" এরর, নাকি অপ্রত্যাশিত bug।
ERROR_MESSAGES[code] ?? codeNullish coalescing (??) — বাম দিকের মান যদি null বা undefined হয়, তাহলে ডান দিকেরটা ব্যবহার হবে। এখানে: যদি কোডের জন্য কোনো readable মেসেজ না থাকে, তাহলে কোডটাই মেসেজ হিসেবে দেখানো হবে।
response.headersSent চেকযদি ইতিমধ্যে response পাঠানো হয়ে গিয়ে থাকে (headers চলে গেছে), তাহলে আবার নতুন response পাঠানো যাবে না — তাই এটা next(error) দিয়ে Express-এর নিজস্ব built-in ডিফল্ট হ্যান্ডলারের কাছে ছেড়ে দেয়।

Arrow function রিটার্ন করা আরেকটা arrow functionvalidate.js-এর মতোই এখানেও higher-order function প্যাটার্ন — asyncHandler(controllerFn) কল করলে একটা নতুন ফাংশন রিটার্ন হয় যেটা Express route-এ বসানো যায়।
Promise.resolve(handler(...))handler যদি একটা Promise রিটার্ন করে (async ফাংশন সবসময়ই করে), Promise.resolve() সেটাকে wrap করে নিশ্চিত করে এটা একটা Promise হিসেবেই ট্রিট হবে, তারপর .catch() চেইন করা যায়।
.catch(next)এটার মানে .catch((error) => next(error))-এরই সংক্ষিপ্ত রূপ — যদি Promise reject হয়, সেই error সরাসরি next ফাংশনে পাস হয়ে যায়, যা Express-কে errorHandler-এ পাঠিয়ে দেয়।

function write(method, level, message, context) {
  method(
    JSON.stringify({
      timestamp: new Date().toISOString(),
      level,
      message,
      ...context,
    }),
  );
}

export const logger = {
  info(message, context = {}) {
    write(console.info, 'info', message, context);
  },

  error(message, error, context = {}) {
    write(console.error, 'error', message, {
      ...context,
      error: error?.message,
      stack: error?.stack,
    });
  },
};
সিনট্যাক্সব্যাখ্যা
logger একটা অবজেক্ট, ক্লাস না{ info() {...}, error() {...} } — দুইটা মেথড সহ একটা প্লেইন অবজেক্ট। যেকোনো ফাইল logger.info(...) বা logger.error(...) ডেকে ব্যবহার করতে পারে, new লাগে না।
Spread operator ...contextএকটা অবজেক্টের সব key-value জোড়া নতুন অবজেক্টে "ছড়িয়ে" দেয়। এখানে caller যে extra context (যেমন { method, path }) দেয়, সেটা মূল লগ অবজেক্টের সাথে মিশে যায়।
error?.messageOptional chaining (?.) — যদি error নিজেই null/undefined হয়, পুরো এক্সপ্রেশন ক্র্যাশ না করে undefined রিটার্ন করে, সরাসরি error.message করলে যা ক্র্যাশ করত।
Shorthand property { level, message }যখন ভ্যারিয়েবলের নাম আর key-এর নাম একই হয় (level: level), শুধু level লিখলেই চলে — এটা ES6-এর "property shorthand"।
কেন JSON.stringify করে?প্রতিটা লগ লাইন এক লাইনের valid JSON — production-এ log aggregator টুল (Datadog, CloudWatch ইত্যাদি) এগুলো সহজে পার্স করে সার্চ/ফিল্টার করতে পারে। মানুষ পড়ার জন্য সুন্দর না, কিন্তু মেশিনের জন্য কার্যকর — একে বলে "structured logging"।

import { pool } from '../config/db.js';

export async function findAll() {
  const { rows } = await pool.query(
    `SELECT
       id,
       name,
       country,
       timezone,

সিনট্যাক্সব্যাখ্যা
Template literal দিয়ে multi-line SQLব্যাকটিক (`) স্ট্রিং একাধিক লাইনে লেখা যায়, যেটা সাধারণ '...' বা "..." দিয়ে সরাসরি সম্ভব না — SQL পড়তে সুবিধা হয়।
$1 আর দ্বিতীয় আর্গুমেন্ট [true]Parameterized query — $1 একটা placeholder, আসল মান (true) আলাদা অ্যারেতে পাঠানো হচ্ছে। pg লাইব্রেরি নিরাপদভাবে এই মান বসায়। এটা কখনো স্ট্রিং concatenation দিয়ে করা হয় না — AGENTS.md-এ স্পষ্ট নিয়ম "parameterized queries only" — কারণ সরাসরি concatenation SQL injection আক্রমণের দরজা খুলে দেয়।
launched_at::text AS "launchedAt"::text হলো PostgreSQL-এর টাইপ cast সিনট্যাক্স (DATE কে TEXT বানানো)। AS "launchedAt" কলামের নাম বদলে দেয় camelCase-এ (SQL কনভেনশনে snake_case, কিন্তু JavaScript/JSON কনভেনশনে camelCase — তাই এখানেই রূপান্তর করা হচ্ছে, ফ্রন্টএন্ডে না)।
Destructuring const { rows } = await pool.query(...)pool.query() একটা অবজেক্ট রিটার্ন করে যাতে অনেক property থাকে (rowCount, fields, ইত্যাদি) — এখানে শুধু rows property-টাই বের করে নেওয়া হচ্ছে।
কোনো SELECT * নেইইচ্ছাকৃতভাবে নির্দিষ্ট কলাম লিস্ট করা হয়েছে — টেবিলে নতুন সেনসিটিভ কলাম যোগ হলেও সেটা accidentally leak হবে না। cities.repository.test.js-এ এটাই টেস্ট করা হয়েছে (assert.doesNotMatch(sql, /SELECT\s+\*/i))।

class একটা ব্লুপ্রিন্ট। extends একটা ক্লাসকে আরেকটার উপর ভিত্তি করে বানায় (inheritance)। this মানে "যে instance-এ এখন কাজ হচ্ছে সেটা"। super() parent-এর constructor চালায় — this ব্যবহারের আগে extends করা ক্লাসে এটা বাধ্যতামূলক।

try/catch/throw 
try {
  await riskyOperation();
} catch (error) {
  // error না ধরলে যা হতো তা এখানে সামলানো হয়
}

throw new Error('কিছু ভুল হয়েছে'); // ইচ্ছাকৃতভাবে এরর তৈরি করে "ছোড়া"
Higher-order function (ফাংশন যা ফাংশন রিটার্ন করে) 
const asyncHandler = (handler) => (request, response, next) => {...};

// ব্যবহার:
router.get('/', asyncHandler(myController)); // asyncHandler(myController) একটা নতুন ফাংশন রিটার্ন করে

জাভাস্ক্রিপ্টে ফাংশনও একটা সাধারণ মান — ভ্যারিয়েবলে রাখা যায়, আর্গুমেন্ট হিসেবে পাস করা যায়, রিটার্নও করা যায়। asyncHandler আর validate দুটোই এই প্যাটার্নে বানানো — একটা ফাংশন যেটা কনফিগারেশন নিয়ে আরেকটা কাস্টমাইজড ফাংশন বানিয়ে দেয়।

Object.freeze() 
export const corsOptions = Object.freeze({ origin: env.CLIENT_ORIGIN });

একটা অবজেক্টকে immutable (অপরিবর্তনীয়) করে দেয় — পরে কেউ corsOptions.origin = 'other' লিখলেও তা চুপচাপ উপেক্ষা হবে (strict mode-এ error দেবে)। কনফিগারেশন অবজেক্টে এটা কমন — যাতে ভুলবশত পরিবর্তন না হয়।
