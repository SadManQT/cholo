Bugs

Found by running every screen as a passenger, driver and admin, and by reading the code behind them.

  • 3.1Driver online toggle broke out of its track

    Fixed

    The knob had no left anchor, so switching to online pushed it outside the switch. The ON/OFF label also sat under the knob.

    client/src/pages/driver/DriverHomePage.tsx

  • 2.2Booking panel cut off and covering the tab bar

    Fixed

    Every bottom sheet was drawn at 90% of the screen and slid down, so at the half and peek positions the confirm button sat below the visible area. Sheets now size themselves and end above the tab bar, on booking, live trip, driver trip, offers and chat.

    client/src/components/ui/BottomSheet.tsx

  • 2.3Map markers were plain circles

    Fixed

    Pickup, drop-off, driver and SOS now use teardrop pins with a shadow, anchored at the tip so they point at the exact spot.

    client/src/components/map/MapView.tsx

  • 1.2Sign-up showed one generic error

    Fixed

    Each field now shows its own reason under a red-bordered input ("Phone number is incomplete (7 of 11 digits)"), and a phone that's already registered is flagged on the phone field.

    client/src/pages/auth/RegisterPage.tsx · server/src/validators/auth.schema.js

  • 1.3"Something went wrong on our side" everywhere

    Fixed

    Validation errors show the specific reason, an unreachable server or timeout says so, and a database outage returns a logged 503 with its own message. The generic text is now only the last resort.

    client/src/utils/apiError.ts · server/src/middlewares/errorHandler.js

  • 6.1SOS board had no map, and short notes failed

    Fixed

    Each open alert shows a live map with where the SOS was sent and the trip's latest position. Notes shorter than the 3 characters the server requires are caught before sending, and each button has its own spinner.

    client/src/pages/admin/SosBoardPage.tsx · server/src/repositories/safety.repository.js

  • "Drive with Cholo" leads to a 404

    Fixed

    After sign-up with the driver option, the app sends people to /driver/apply, which doesn't exist. There is also no screen to add a vehicle or upload documents, so nobody can become a driver from the app.

    client/src/pages/auth/OtpVerifyPage.tsx · client/src/App.tsx

  • Toasts cover the mobile tab bar

    Fixed

    Messages appear over Book / Trips / Wallet / Account, blocking the tabs for a few seconds after every action.

    client/src/components/ui/Toast.tsx

  • Menu items open "coming soon" screens

    Fixed

    Six links lead to placeholder pages: driver documents, driver vehicles, promos, payment methods, saved places and admin zones.

    client/src/App.tsx

  • Sign-up can leave a half-created account

    Fixed

    Creating the user, giving it the passenger role and sending the code are separate steps with no transaction. If one fails, the phone number is taken but the account can't log in.

    server/src/services/auth.service.js

  • Every page reload would sign users out in production

    Fixed

    The refresh cookie was SameSite=strict. With the site on Vercel and the API on Render, the browser never sends it, so sessions could not be restored after a reload.

    server/src/controllers/auth.controller.js

  • All riders would share one login rate limit on Render

    Fixed

    The API did not trust the host's proxy, so every request looked like it came from the same IP. A few failed logins anywhere would lock everyone out.

    server/src/app.js

  • Driver approvals and Document review failed to load

    Fixed

    The vehicle queue queried a column that did not exist, and both admin pages load that queue, so both showed "Queue did not load".

    database/migrations/0005_launch_features.sql

  • Rejection reasons never reached drivers

    Fixed

    Reasons for rejecting a driver, a vehicle or a vehicle document were only written to the audit log. They are now stored, shown to the driver and sent as a notification.

  • Drivers landed on the rider screen after logging in

    Fixed

    Every driver is also a passenger, and the home screen checked the passenger role first. The Account page now also switches between riding and driving.

    client/src/utils/roleHomePath.ts

  • "Forgot password?" opened a placeholder

    Fixed

    The login link pointed at an unfinished screen; it now opens the real reset flow.

  • Active users showed a red status pill

    Fixed

    The pill reused the SOS board's red for every "active" state, so healthy accounts looked like alerts in the Users list.

    client/src/components/ui/StatePill.tsx

Features built

What riders, drivers and the ops team need for the product to feel finished.

Accounts & safety

  • 1.1Forgot password

    Done

    "Forgot password?" on login sends a 6-digit code to the phone, then lets the person set a new password. The code expires, attempts are limited, and every other session is signed out.

  • 5.4Timed suspensions

    Done

    Admins choose Permanent, 1 week, 1 month or a custom end date. Accounts come back automatically when the time is up, and the person sees the reason and end date when they try to log in.

  • Emergency contacts

    Done

    Riders add the people who should hear about an SOS. The SOS flow already reads this list; there was no way to fill it.

  • Notifications

    Done

    A bell with unread count for every role: driver application decisions, document reviews, dispute outcomes, support replies and suspensions.

Riders

  • 2.1Saved places and recent trips on the booking screen

    Done

    Home, University and custom places plus recent drop-offs appear as one-tap shortcuts under From / To, with a page to add, rename and remove places.

  • Rate your trip

    Done

    After a completed trip both sides give 1–5 stars and an optional comment. Averages appear on driver cards and in admin.

  • Promos page

    Done

    Shows the codes available in the rider's city, with terms and expiry.

  • 4.1Dispute lifecycle and support threads

    Done

    Disputes move Opened → Under review → Resolved, with each step's time visible to the person who raised it. Only that person and admins can see a dispute; the other party on the trip can't.

Drivers

  • Driver onboarding

    Done

    Apply with NID and license, add a vehicle, and upload the required documents, with a checklist showing what's approved, pending or rejected and why.

  • Document and vehicle pages

    Done

    Replace the placeholders with real screens: upload or replace a document, see expiry dates, choose which approved vehicle is active.

Operations

  • 5.1 · 5.2Approvals and document review

    Done

    The queues already exist. Adding in-page image and PDF previews, "expiring soon" and "expired" flags, a nightly job that expires old documents, and a notification to the driver on every decision.

  • 5.3Zones

    Done

    Create, edit and delete zones by clicking points on the map. Restricted zones block pickups and drop-offs, and drivers are tagged with the zone they're in so the dashboard can count them.

  • Admin shell

    Done

    Brand, icons, the signed-in admin and a sign-out button in the sidebar; notifications in the header.

Deploy readiness

  • Health check and security headers

    Done

    A /health endpoint that checks the database for the host's uptime probe, standard security headers, correct client IPs behind the host's proxy (rate limits depend on it), and a clean shutdown.

  • Crash screen

    Done

    If a screen throws, show a friendly "reload" page instead of a blank white screen.

  • Document uploads

    Done

    Drivers upload photos or PDFs instead of pasting links. Files are stored by the API with type and size limits.

Needs an outside provider

These need an account, keys or a contract before launch. The code has a clear place to plug each one in.

  • Real SMS delivery

    Needs a provider

    Sign-up and password-reset codes are only written to the server log today. Connect an SMS gateway (e.g. SSL Wireless, Alpha SMS or Twilio).

    server/src/services/sms.service.js

  • Permanent file storage

    Needs a provider

    Uploaded documents are saved on the API server's disk, which Render wipes on every deploy. Move them to object storage such as Cloudflare R2 or S3.

  • Live payments

    Needs a provider

    SSLCommerz runs in sandbox mode. bKash and Nagad need merchant accounts and live credentials.

  • Push notifications

    Needs a provider

    In-app notifications work while the app is open. Reaching people with it closed needs Firebase Cloud Messaging.

  • Maps and routing at scale

    Needs a provider

    Routing and search use the free public OSRM and Photon servers, which rate-limit heavy traffic. Self-host them or pay for a plan before launch.

  • Error monitoring and CI

    Needs a provider

    Send server and browser errors to a service like Sentry, and run the 340 server tests plus the client build on every pull request.

Later, once the basics ship: referrals, favourite drivers, automatic surge pricing, monthly invoices for drivers, and a full Bangla translation. The database already has tables for most of these.
