The two ideas that confuse everyone

1. The frontend and backend are two separate programs

This is the biggest mental shift from JavaFX. In a JavaFX app, your button handler can call a database method directly — same program, same memory. Here they are two processes that don't share memory. They talk only by sending HTTP messages over the network.

Browser (React) port 5173
Draws the screen. Has no database access at all, and no passwords.
↓  HTTP request with a JWT  ↓
Express API (Node) port 3000
Checks who you are, checks what you're allowed to do, runs the business rules, talks to Postgres.
↓  SQL over a pooled connection  ↓
PostgreSQL port 5433
Stores everything. Enforces constraints as the final line of defence.
Why this matters for your grade

Because they're separate programs, hiding a button in React hides nothing. Anyone can open Postman and call the API directly. That's exactly why the guidelines say authorization must be enforced in the backend — and why we check roles and ownership on the server in every single route.

2. "Asynchronous" and await

Database calls take time. Node does not block and wait like Java does by default — it goes off and does other work. The await keyword means "pause this function until the result comes back, but let the server keep handling other requests meanwhile."

// This reads top-to-bottom exactly like Java. The await just means
// "the server can serve other people while this query runs".
const user = await usersRepo.findAuthByPhone(phone);
const matches = await verifyPassword(password, user.passwordHash);

Any function containing await must be declared async. That's the whole rule.

The five backend layers, and the rule for each

routes/ rides.routes.js
Maps a URL + verb to a handler, and lists the gates it must pass. No logic. This is where you can read the security policy of an endpoint in one line.
↓
middlewares/ auth.js, validate.js
Runs before the controller and can reject. Is there a valid token? Does the body match the schema? Is this role allowed?
↓
controllers/ rides.controller.js
Translates HTTP to plain values and back. Reads req.body, req.user.id, calls one service function, sets the status code. Never contains business rules and never contains SQL.
↓
services/ rides.service.js
The actual thinking. Fare calculation, "can this passenger book right now?", transactions, ownership checks, calling other services. Knows nothing about HTTP.
↓
repositories/ rides.repository.js
SQL, and only SQL. One function per query. Takes plain arguments, returns plain rows. No business decisions.
Say this when asked about your architecture

"It's a layered architecture. Each folder is a layer with one job, and each file inside is one feature. A request goes route → middleware → controller → service → repository → PostgreSQL, then the result travels back the same way. SQL is only permitted in repositories/, which means we can audit every query in the system by looking in one folder. Controllers never contain business logic and services never know they're being called over HTTP — which is why the services are testable without a web server."

SECTION 05

What runs first

"Which file executes first?" is a favourite viva question. Here is the exact order, both sides.

Backend boot — npm run dev

Node loads src/server.js

server/src/server.js

This is the entry point named in package.json. Its import statements run first, which pulls in everything below before a single line of its own body executes.

config/env.js validates the environment

server/src/config/env.js

Reads the root .env file and runs it through a Zod schema. If DATABASE_URL is missing or JWT_SECRET is shorter than 32 characters, the server refuses to start with a readable error. Failing loudly at boot beats failing mysteriously at 2am.

config/db.js creates the connection pool

server/src/config/db.js
export const pool = new Pool({ connectionString: env.DATABASE_URL });

Note it does not connect yet — the pool opens connections lazily on first use.

app.js assembles the Express application

server/src/app.js

Registers the global middleware chain in order (CORS → JSON parser → cookie parser → request logger), mounts /health, mounts every API route under /api/v1, then finally the 404 handler and the error handler.

routes/index.js mounts the 16 routers

server/src/routes/index.js

Each feature router gets a URL prefix: /auth, /rides, /admin, /trips, etc. Combined with the /api/v1 prefix, that's how POST /api/v1/auth/login finds its handler.

The port opens

server/src/server.js
const server = app.listen(env.PORT, () => {
  console.log(`Cholo API listening on port ${env.PORT}`);
});

This is the first line of server.js's own body to run, and the message you see in your terminal.

Socket.io attaches to the same server

server/src/sockets/index.js

One Node process, one HTTP server, one port. Express handles normal /api/* requests; Socket.io intercepts connections that ask to upgrade to WebSocket.

The cron job starts

server/src/jobs/expireRequests.job.js

Every minute, it marks ride requests older than 5 minutes as expired and withdraws their pending offers.

Why are sockets and cron in server.js instead of app.js?

Because the test suite imports app.js directly to fire fake HTTP requests at it. If sockets and cron lived in app.js, every test run would open a real port and start a background timer. Splitting the entry into two files keeps app.js a pure, side-effect-free Express app. That's a deliberate design decision and a great thing to be able to explain.

Frontend boot — opening localhost:5173

index.html loads

client/index.html

An almost empty page. It contains <div id="root"></div> and one script tag pointing at /src/main.tsx. This is a single-page application: the server sends one HTML shell and JavaScript builds everything else.

main.tsx mounts React into that div

client/src/main.tsx
createRoot(document.getElementById('root')!).render(
  <BrowserRouter>
    <AuthProvider>

      </SocketProvider>

Read it outside-in: routing wraps auth, auth wraps sockets, sockets wrap the app. Anything inside can ask "who is logged in?" and "is the socket connected?".

On mount it calls GET /api/v1/me. There's no access token in memory yet on a fresh page load, so that returns 401 — which automatically triggers the refresh-cookie flow. If you had a valid session, you're silently logged back in. If not, the 401 just means "not logged in" and the app shows the marketing page.

App.tsx picks a page from the URL

client/src/App.tsx

React Router matches the current URL against the route table and renders the matching page, wrapped in a ProtectedRoute that checks your role.

Trace A: the Login button

The single most valuable thing in this handbook. If you can narrate these 13 steps, you understand the whole system — every other feature is this same shape.

Setup: Nusrat types 01710000001 and DemoPass123, and clicks Log in.

The browser fires the form's submit handler

client/src/pages/auth/LoginPage.tsx

The button is type="submit" inside a <form onSubmit={handleSubmit}>. Clicking it runs handleSubmit. In JavaFX terms this is your setOnAction handler.

async function handleSubmit(event) {
  event.preventDefault();      // stop the browser's own page reload
  setSubmitting(true);         // re-renders → button shows a spinner
  const user = await login(phone, password);
  navigate(roleHomePath(user.roles), { replace: true });
}

setSubmitting(true) is the React idea in miniature: you change state, and React redraws the button as disabled with a spinner. You never touch the DOM yourself.

The page calls login() from AuthContext

The page doesn't know how logging in works. It asks the shared auth context, which is available to every component in the app.

async function login(phone, password) {

}

The API layer sends the actual HTTP request

client/src/api/auth.api.ts
const { data } = await apiClient.post('/auth/login', { phone, password });
setAccessToken(data.data.accessToken);   // stored in memory only
return data.data.user;

This is the boundary. Everything above is browser; everything below is server. A real POST now travels to http://localhost:3000/api/v1/auth/login carrying JSON.

Architectural rule worth quoting

Components never call axios directly — only files in api/ do. That's why token handling exists in exactly one place, and why no page has ever seen a raw token.

Express receives it and runs the global middleware chain

server/src/app.js
app.use(cors(corsOptions));   // 1. is localhost:5173 allowed to call us?
app.use(express.json());      // 2. parse the JSON body into req.body
app.use(cookieParser());      // 3. parse cookies into req.cookies
app.use(requestLogger);       // 4. start a timer, log when finished
app.use('/api/v1', apiRouter);

These run in the order written, on every request. Order matters: express.json() must come before anything that reads req.body.

The router matches the URL

server/src/routes/index.js → auth.routes.js

/api/v1 strips off, /auth selects the auth router, /login selects this line:

router.post('/login', loginLimiter, validate(loginSchema), authController.login);

Read left to right — that line is the security policy: rate-limit it, validate it, then handle it.

Rate limiter: too many failed attempts?

server/src/middlewares/rateLimit.js

Keyed by phone + IP so an attacker can't lock out everyone sharing an IP. 8 failed attempts per 15 minutes in production. Successful logins don't count — logging in nine times legitimately shouldn't throttle you.

If exceeded: 429 RATE_LIMITED and the chain stops here.

Validation: does the body have the right shape?

server/src/middlewares/validate.js + validators/auth.schema.js
export const loginSchema = z.object({
  phone: z.string().regex(/^01[3-9][0-9]{8}$/, '...valid Bangladeshi number'),
  password: z.string().min(1).max(72),
});

If it fails, the request never reaches your code — it returns 422 VALIDATION_FAILED with a per-field list. If it passes, req.body is replaced with the parsed, type-clean version.

First line of SQL-injection defence

Note that phone can only ever be 11 digits matching that regex. A string like ' OR 1=1-- is rejected here, before it ever reaches the database — and even if it got through, the query is parameterized. Two independent fences.

The controller unwraps HTTP and calls the service

server/src/controllers/auth.controller.js
export const login = asyncHandler(async (request, response) => {
  const { accessToken, refreshToken, user } =
    await authService.login(request.body, deviceFromRequest(request));

  setRefreshCookie(response, refreshToken);
  response.json({ success: true, data: { accessToken, user } });
});

Notice how thin it is. It knows about request and response; it makes no decisions. asyncHandler wraps it so that any thrown error is forwarded to the central error handler instead of crashing Node.

The service applies the actual rules

server/src/services/auth.service.js
export async function login({ phone, password }, device) {
  const user = await usersRepo.findAuthByPhone(phone);

  // Always compare, even when no user was found (against a dummy hash)
  // so response timing can't reveal whether the phone exists.
  const passwordMatches = await verifyPassword(password, user?.passwordHash);

  if (!user || !passwordMatches) throw new AppError(401, 'BAD_CREDENTIALS');
  if (user.status === 'suspended') throw new AppError(403, 'ACCOUNT_SUSPENDED');
  if (user.status !== 'active') throw new AppError(401, 'BAD_CREDENTIALS');

  return mintSession(user.id, device);
}
She will ask about that dummy-hash line

"If we skipped the bcrypt comparison when the user doesn't exist, that response would come back in 2ms instead of 250ms. An attacker could time our responses to discover which phone numbers are registered. So we always run a comparison — against a real hash of a random password when there's no user — making both paths take the same time." That's called a timing attack, and defending against it is worth marks.

The repository runs the SQL — this is the query

server/src/repositories/users.repository.js
export async function findAuthByPhone(phone) {
  const { rows } = await pool.query(
    `SELECT id, public_id AS "publicId", full_name AS "fullName", phone,
            password_hash AS "passwordHash", status, phone_verified_at
     FROM users
     WHERE phone = $1`,
    [phone],
  );
  return rows[0];
}

$1 is the whole SQL-injection defence. The SQL text and the value travel to PostgreSQL separately. Postgres parses the query first, then binds phone as data. It is structurally impossible for the value to become executable SQL. See section 09.

Password check with bcrypt

server/src/utils/password.js
export function verifyPassword(password, hash) {
  return bcrypt.compare(password, hash ?? DUMMY_HASH);
}

We never decrypt anything — hashing is one-way. bcrypt reads the salt and cost factor out of the stored hash, hashes the submitted password the same way, and compares. Cost 12 means 212 rounds, roughly 250ms, deliberately slow to make brute force expensive.

Mint the session — three database writes

server/src/services/auth.service.js → mintSession()
  1. Read the roles from SQL — SELECT r.name FROM user_roles ur JOIN roles r .... The role comes from the database, never from the client.
  2. Insert a login_sessions row recording device type, IP and user-agent.
  3. Sign a JWT access token containing the user id, roles and session id, expiring in 15 minutes.
  4. Generate a random refresh token, store only its SHA-256 hash in refresh_tokens, and return the raw value once.

The response travels back and React re-renders

back up the whole chain

The controller puts the refresh token in an httpOnly cookie (JavaScript cannot read it, so an XSS bug can't steal it) and the access token in the JSON body. Back in the browser: setAccessToken() keeps it in a plain variable in memory, AuthContext stores the user in state, that state change re-renders the app, and navigate(roleHomePath(user.roles)) sends Nusrat to /, Rafiq to /driver, Ayesha to /admin.

The 30-second version, for the viva

"The click calls a submit handler, which calls our auth context, which calls our API layer, which sends POST /api/v1/auth/login. On the server it passes CORS, JSON parsing, a rate limiter and Zod validation, then the controller calls the auth service. The service looks the user up by phone with a parameterized query, compares the password with bcrypt, reads the roles from the user_roles table, creates a session row, signs a 15-minute JWT and issues a refresh token whose hash is stored in the database. The response carries the access token in JSON and the refresh token in an httpOnly cookie. React stores the user in context and redirects to the role's home page."

The transaction opens

export async function withTransaction(work) {
  const client = await pool.connect();   // one dedicated connection
  try {
    await client.query('BEGIN');
    const result = await work(client);
    await client.query('COMMIT');
    return result;
  } catch (error) {
    await client.query('ROLLBACK').catch(() => {});
    throw error;
  } finally { client.release(); }
}
Why one connection matters

Part 3 — the accept race (the best question you'll get)

Five drivers now have the same offer on screen with a 15-second timer. Two tap Accept at the same millisecond. Exactly one must win, and the other must be told cleanly.

The lock — this is the whole answer

repositories/rides.repository.js → findForUpdate()
SELECT ... FROM ride_requests WHERE id = $1 FOR UPDATE

FOR UPDATE takes an exclusive row lock. Driver A gets it. Driver B's query blocks — it does not fail, it waits for A's transaction to finish.

Driver A does all the work and commits

Driver B's query unblocks and re-reads

B's SELECT ... FOR UPDATE now returns — and because it re-reads the row after A committed, it sees status = 'matched', not 'searching'. So:

throw new AppError(409, 'ALREADY_TAKEN');

B's transaction rolls back cleanly. Their app shows "Too late — another driver accepted it." No corruption, no double booking.

The database backstop

Even if the lock were somehow bypassed, trips.request_id is UNIQUE — a second trip for the same request is physically unstorable. The application catches that unique violation and converts it to the same 409.

Say exactly this when asked about the race condition

"We lock the ride request row with SELECT ... FOR UPDATE inside a transaction. The second driver's query blocks rather than failing, and when it unblocks it re-reads the row and sees the status is already matched, so it returns 409 ALREADY_TAKEN. We also have a UNIQUE constraint on trips.request_id as a database-level backstop, so even a bug in our application logic couldn't create two trips for one request. Application logic prevents it; the constraint makes it impossible."

Parameterized queries — how $1 actually protects you

Every query in the codebase looks like this:

pool.query(
  `SELECT id, password_hash FROM users WHERE phone = $1`,
  [phone],
);

The SQL text and the values are sent to PostgreSQL as two separate things. Postgres parses and plans the query first, using $1 as a typed placeholder. Only then does it bind the value. The value is never parsed as SQL — it can only ever be data.

What the vulnerable version would look like

// WE DO NOT DO THIS ANYWHERE. This is the SQL-injection defect
// the guidelines penalise.
pool.query(`SELECT * FROM users WHERE phone = '` + phone + `'`);

If phone were ' OR '1'='1 the database would receive WHERE phone = '' OR '1'='1' and return every user. With $1 it searches for a user whose phone is literally the string ' OR '1'='1, finds none, and returns nothing.

She may grep your code for ${ in SQL. Have this ready.

There are a few template literals inside SQL strings — and every one of them interpolates a hard-coded constant or a whitelisted column name, never user input. Two examples worth being able to defend:

  • users.repository.js — updateProfile() builds a SET clause dynamically, but the column names come from a fixed PROFILE_COLUMNS map, and Zod has already restricted the keys. The values are still $2, $3, ….
  • admin.repository.js — listUsers() builds const pattern = \`%${search}%\`, which looks alarming but is passed as bind parameter $2. It builds a value for ILIKE, not SQL text.

Say: "We interpolate column names from a fixed whitelist so a user can never inject one. All user-supplied values, without exception, go through bind parameters."

Transactions

A transaction groups several statements so they all succeed or all fail. Booking a ride inserts a request and several offers — a crash between them must not leave a request nobody was offered.

await withTransaction(async (client) => {
  await ridesRepo.lockPassengerBooking(passengerId, client);
  const inserted = await ridesRepo.insertRequest({...}, client);
  await dispatchService.fanOutOffers({...}, client);
  return inserted;
});  // COMMIT here, or ROLLBACK if anything threw

Notice client being threaded through every call. Every repository function takes an optional client and falls back to the pool: async function insertRequest(data, client = pool). That one pattern lets the same function work inside or outside a transaction.

Used in five places, always for the same reason: a check followed by a write, where a second request must not slip between them.

"Why ON DELETE RESTRICT on trips?"

"A trip is financial history. If someone deleted a user, cascading that delete would silently erase completed trips, earnings and receipts. RESTRICT refuses the delete instead. Two design decisions worth volunteering

Money is NUMERIC, never float
NUMERIC(12,2). Floating point can't represent 0.1 exactly; with money those errors accumulate into real missing taka. In JSON, money is serialised as a string to avoid JavaScript's float conversion.
Time is TIMESTAMPTZ, never naive
Every timestamp carries a timezone. Bangladesh is UTC+6; a naive timestamp is ambiguous the moment a server runs in another region.
Two IDs per row
An internal BIGINT id for joins and a public UUID public_id exposed in the API. Sequential IDs would let anyone count your users or enumerate records.
Fares are snapshotted
A trip stores its own fare breakdown rather than pointing at a pricing rule. Change prices tomorrow and yesterday's receipts stay correct.

JWT — what's actually inside

Three base64 segments separated by dots: header.payload.signature. The payload from a real login tonight:

{
  "roles": ["PASSENGER"],   // read from the DB at login, not from the client
  "sid": "693",             // login_sessions row id
  "iat": 1788784719,        // issued at
  "exp": 1788785619,        // expires — 15 minutes later
  "sub": "4904"             // the user id

The trap question: "isn't a JWT just base64? Can't I edit it?"

Answer: "The payload is only encoded, not encrypted — anyone can read it, which is why we put no secrets in it. But it's signed with a server-side secret using HMAC-SHA256. If you change roles to ADMIN and re-encode, the signature no longer matches, jwt.verify throws, and you get 401. You cannot forge one without JWT_SECRET, which lives only in our git-ignored .env."

"Why two tokens instead of one?"

"It's a trade-off between speed and revocability. Checking the access token needs no database query at all — just a signature check — so it's fast on every request. The cost is that we can't revoke it early, so we keep it alive only 15 minutes. Revocation lives on the refresh side, which is stored in the database and can be killed instantly. Why the access token isn't in localStorage

Anything in localStorage is readable by any JavaScript on the page — one XSS bug and your token is gone. Ours lives in a module-level variable that disappears on refresh, and the refresh token is httpOnly, meaning JavaScript cannot read it at all. The cookie also carries sameSite: 'strict' (CSRF defence) and secure in production (HTTPS only).

Refresh rotation and theft detection

Each refresh rotates: the old token is revoked the instant a new one is issued. If a token that was already rotated is presented again, that means someone is replaying a dead token — so we kill the entire session, not just that token.

if (record.revokedAt) {
  // Could be the user's stale copy or a thief's stolen copy — no way
  // to tell, so treat it as a compromise and end the whole session.
  await sessionsRepo.revokeActiveForSession(record.sessionId, client);
  await sessionsRepo.endSession(record.sessionId, client);
  throw new AppError(401, 'REFRESH_REUSED');
}

The guidelines call out "not merely a redirect on the frontend". Ours does three things:

For a ride-hailing app a 15-minute window is an acceptable trade; for banking it wouldn't be."

Why sockets at all?

  try {
    const claims = jwt.verify(token, env.JWT_SECRET);   // same secret, same check
    socket.user = { id: Number(claims.sub), roles: claims.roles, sessionId: claims.sid };
    next();
  } catch { next(new Error('TOKEN_EXPIRED')); }
}

Running and architecture

Walk me through what happens when you click Login.
See section 06. The 30-second version: submit handler → auth context → api layer → POST /api/v1/auth/login → CORS, JSON parse, rate limit, Zod validate → controller → service → repository runs a parameterized SELECT → bcrypt compare → roles read from user_roles → session row inserted → JWT signed → refresh token hashed and stored → response with token in JSON and refresh in an httpOnly cookie → React stores the user and redirects to the role's home.
Which file runs first?
server/src/server.js on the backend — it validates the environment, builds the Express app from app.js, opens port 3000, attaches Socket.io and starts the cron job. On the frontend, index.html loads src/main.tsx, which mounts React into a single <div id="root">.
Why is the frontend a separate program from the backend?
Separation of concerns and deployability — the React app is static files that can go on any CDN, the API scales independently. The security consequence is the important one: because they're separate, the frontend can't be trusted, so every rule is enforced on the server.
What is Vite doing?
It's the frontend build tool. In development it serves the app and hot-reloads on save; for production npm run build compiles TypeScript and JSX into plain JavaScript bundles. The browser can't run .tsx directly — Vite is what makes it runnable.
What is Express actually giving you?
Routing — mapping a URL and HTTP verb to a function — and a middleware chain, which is how we run authentication, validation and rate limiting before a handler in a declarative, readable way.
Why Docker for the database?
Both of us get an identical PostgreSQL 16 with the same config, without installing Postgres locally. docker-compose.yml pins the version, wires the volume for persistence, and runs the schema on first boot, so a fresh clone reaches a working database in one command.

Database

Where are your queries?
All in server/src/repositories/, 27 files, one per feature. No SQL exists anywhere else in the codebase — that's an enforced convention, and it means the whole data-access surface can be audited in one folder.
Show me you're safe from SQL injection.
Every query uses bind parameters: WHERE phone = $1 with the value passed separately in an array. PostgreSQL parses the SQL before the value is bound, so a value can never become executable SQL. We also validate every input with Zod first — two independent fences. The few template literals in SQL strings interpolate whitelisted column names, never user input.
Did you use an ORM?
No — it's prohibited. We use the pg driver and hand-written SQL.
What is a connection pool and why use one?
Opening a TCP connection to Postgres and authenticating is expensive. The pool keeps a set of open connections and hands one out per query, then takes it back. Without it, every request would pay full connection setup cost.
Explain a transaction in your code.
Booking a ride inserts a ride_requests row and several ride_offers rows. Those must all succeed or all fail, so withTransaction checks out one connection, issues BEGIN, runs the work, and COMMITs — or ROLLBACKs on any error. The single connection matters: a transaction is a property of a connection, so we thread that client through every repository call inside.
What is SELECT ... FOR UPDATE?
An exclusive row lock held until the transaction ends. We use it wherever we read a value, decide from it, and then write — so a concurrent request can't slip between the read and the write. The second transaction blocks and waits, then re-reads the updated row.
Why NUMERIC for money?
Floating point can't represent decimal fractions exactly, so repeated arithmetic drifts. With money that becomes real missing taka. NUMERIC(12,2) is exact decimal. We also serialise money as a string in JSON so JavaScript's float handling can't corrupt it.
Why TIMESTAMPTZ?
It stores an absolute instant with timezone awareness. A naive timestamp is ambiguous the moment the server, the database and the user are in different regions.
Why do rows have two IDs?
A BIGINT id for internal joins, which is compact and fast, and a UUID public_id for the API. Exposing sequential IDs would let anyone count our users or walk through records by incrementing a number.
Give me an example of a CHECK constraint.
CHECK (phone ~ '^01[3-9][0-9]{8}$') on users. The same rule exists in our Zod validator. The application gives a friendly error; the constraint guarantees no bad row can exist even if it were inserted by something other than our API.
Why RESTRICT instead of CASCADE on trips?
A trip is financial and legal history. Cascading a user delete would erase completed trips, earnings and receipts. RESTRICT refuses; we soft-delete users by setting status = 'deleted'. We use CASCADE only where the child is meaningless alone, like user_roles.

Authentication

How are passwords stored?
bcrypt hashes at cost factor 12. Never plain text, never reversible. bcrypt generates a random per-password salt and embeds it in the hash string, so two identical passwords produce different hashes and rainbow tables don't work.
Where's the salt?
Inside the hash. $2b$12$<salt+hash> — the algorithm, the cost factor and the 22-character salt are all encoded in the stored string.
What's in your JWT?
User id (sub), roles, session id, issued-at and expiry. Nothing secret — the payload is only base64-encoded, not encrypted, so anyone can read it.
Then can't I edit it and make myself admin?
No. It's signed with HMAC-SHA256 using a server-side secret. Change any byte and the signature stops matching, jwt.verify throws, and you get 401. Forging one requires JWT_SECRET, which is only in our git-ignored .env. I can demonstrate this in jwt.io and Postman.
Where does the role come from?
From the database. At login we JOIN user_roles with roles and sign the result into the token. The client never sends its role — the guidelines specifically warn about trusting a client-supplied role, and we don't.
Why two tokens?
Speed versus revocability. The access token is stateless so checking it costs no database query, but that means we can't revoke it — so it lives 15 minutes. The refresh token is stored (hashed) in the database, lives 30 days, and can be killed instantly. See section 11.
Why not store the token in localStorage?
Any JavaScript on the page can read localStorage, so one XSS bug leaks the token. Ours lives in a module-level variable in memory, and the refresh token is in an httpOnly cookie that JavaScript cannot read at all.
Does logout really invalidate the session?
Yes. We set revoked_at on the refresh token row and is_active = false on the session row, and clear the cookie. After logout, POST /auth/refresh returns 401 — I can show that in Postman. The old access token remains valid until it expires, which is the documented trade-off of stateless access tokens.
What stops OTP brute force?
Three things. The code expires in 5 minutes. There's a hard cap of 5 attempts per code, enforced under a FOR UPDATE lock so parallel guesses can't all read the same stale counter. And a rate limiter keyed on phone+IP. The OTP is also stored as a SHA-256 hash, not plain text.
What is refresh token rotation?
Every refresh issues a new token and revokes the old one immediately. If an already-rotated token is presented again, someone is replaying a dead token — we can't tell whether it's the real user or a thief, so we end the entire session rather than just rejecting that one token.

Authorization

How do you stop a passenger calling an admin endpoint?
requireRole('ADMIN') middleware on the admin router. It reads the roles that auth verified from the signed token and returns 403 otherwise. Let me show you in Postman.
How do you stop me reading someone else's trip by changing the ID?
Ownership checks in the service layer. Every trip lookup compares the trip's passenger and driver IDs against the authenticated user's ID and throws 404 if it doesn't match. Because it's in the service, it applies regardless of which endpoint reaches it.
Why 404 and not 403 for someone else's record?
403 would confirm the record exists, letting an attacker enumerate valid IDs by watching the status code. 404 for both "doesn't exist" and "not yours" leaks nothing.
Your React app also checks roles — isn't that the mistake in the guidelines?
The mistake is checking only on the frontend. Ours duplicates a server-side check purely so users don't see broken screens. Deleting our entire frontend wouldn't weaken security — Postman still gets 401 and 403.
Is being an ADMIN enough to approve a payout?
No. The role gets you past the route gate, then the withdrawal service re-reads admin_profiles.access_level from the database and requires finance. That's deliberately not in the JWT, so it's re-checked at decision time.

Features and design

Two drivers accept the same ride at once. What happens?
See section 07, part 3. Row lock with FOR UPDATE, second driver blocks then re-reads and sees matched, gets 409 ALREADY_TAKEN. A UNIQUE constraint on trips.request_id makes a double booking physically impossible as a backstop.
Why are ride_requests, ride_offers and trips three separate tables?
They have different lifecycles. A request is demand — it can expire with no trip. An offer is one marketplace attempt — many per request, and the data behind driver acceptance rates. A trip is fulfilment — it exists only when someone accepted. Collapsing them would lose the ability to analyse unmet demand or driver behaviour.
How is the fare calculated?
Look up the effective-dated pricing rule for that city and vehicle category, get distance and duration from an OSM routing service, then base fare + per-km + per-minute, multiplied by surge, clamped to a minimum. The result is snapshotted onto the ride request — the server recomputes it at booking and never trusts a price sent by the client.
What if the passenger's browser closes mid-search?
A cron job runs every minute and marks requests past their 5-minute window as expired, withdrawing any still-pending offers. On return, the app restores the active request from its public ID.
How does the driver get the offer without refreshing?
Socket.io. After the booking transaction commits, the server emits offer:new to that driver's room. The push is deliberately thin — it just says something arrived, and the app then fetches the full offer over REST. The driver app also polls every 5 seconds as a fallback.
Why emit after the commit and not inside the transaction?
Because a later statement in the same transaction could still roll back. Notifying a driver about an offer that then ceases to exist would be a real bug. We capture what to send inside the transaction and emit only after COMMIT.
What did you deliberately not build?
Scheduled-ride dispatch, multi-stop trips, PDF receipts, a zone polygon editor, and real SOS SMS fan-out. Surge pricing needs point-in-polygon zone resolution, which needs PostGIS — rather than fake it we default the multiplier to 1.00 and left the column and the seam in place. Naming a conscious cut is much stronger than pretending everything is finished.
How do you know it works?
317 automated tests — unit tests for pure logic like fare and commission math, integration tests for wallet locking and ledger immutability, and API tests that fire real HTTP requests at the app and assert status codes and bodies. Each test file runs inside a transaction that's rolled back, so tests never pollute the database. npm test at the root also runs the frontend lint and a production build.
Which part did you find hardest?
Be honest and specific — the accept race. "Getting the ordering right: lock the request, re-check the status after acquiring the lock, do the writes, commit, and only then emit sockets. Our first instinct was to check the status before locking, which is exactly the bug the lock exists to prevent."

What changed tonight

Two fixes were made while preparing this. You should know about them, because one is a security bug worth mentioning proactively.

Fix 1 — the OTP lockout never actually locked out

The bug. verifyOtp incremented the failed-attempt counter and then threw an error to signal "wrong code" — but both happened inside withTransaction. Throwing triggers ROLLBACK, which undid the increment. The counter was permanently stuck at 0, so the 5-attempt cap could never trigger. Proven live: seven wrong guesses all returned 401, with attempts still 0 in the database.

The fix. Failures are now returned out of the transaction rather than thrown from inside it, and raised only after the commit. The FOR UPDATE lock still covers the whole check-then-increment sequence, so parallel guesses stay serialized.

// server/src/services/auth.service.js
if (hashOtp(otp) !== record.otpHash) {
  await otpRepo.incrementAttempts(record.id, client);
  return { failure: new AppError(401, 'OTP_INVALID') };  // return, don't throw
}
// … after the transaction commits:
if (outcome.failure) throw outcome.failure;

Verified after the fix:

attempt 1 → HTTP 401   | attempts in DB: 1
attempt 2 → HTTP 401   | attempts in DB: 2
attempt 3 → HTTP 401   | attempts in DB: 3
attempt 4 → HTTP 401   | attempts in DB: 4
attempt 5 → HTTP 401   | attempts in DB: 5
attempt 6 → HTTP 429   | attempts in DB: 5
attempt 7 → HTTP 429   | attempts in DB: 5
This is worth raising yourself

"One thing we found while reviewing: our OTP attempt counter was being rolled back by the same transaction that reported the failure, so the lockout never engaged. We fixed it by committing the increment and raising the error after the transaction. It's a good example of why a rollback isn't always what you want — the failure itself was the thing we needed to record."

Volunteering a bug you found and fixed, with a clear explanation of the mechanism, reads as engineering maturity. It's a genuinely interesting transaction-semantics point in a database course.

tests/api/wallet.test.js mocked pool.query but not pool.connect. Adding the same pool.connect mock its sibling test files already use — translating BEGIN/COMMIT/ROLLBACK into savepoints on the shared client — fixed all six.
