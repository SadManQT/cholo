What Cholo is

Cholo (চলো, "let's go") is a ride-sharing app for Bangladesh, like Pathao or Uber. It has three kinds of users:

Passenger

Picks where to go, sees the price, books a ride, watches the car come, pays, and rates the driver.

Driver

Uploads documents, gets approved, goes online, receives ride offers, drives, earns money, and withdraws it.

Admin

Approves drivers, sets prices, handles emergencies and complaints, and watches revenue.

The one trick that always works

For any line you don't understand, ask two questions: who calls this? and what does it give back? Every feature is the same chain: button → API function → route → controller → service → repository → SQL → database. The answer travels back along the same chain.

Think of a restaurant
  • The customer is the person using the phone or laptop.
  • The menu and order pad are the React screens. They show choices and write down what the customer wants.
  • The waiter carries the order to the kitchen. That's an HTTP request.

Chapter 05

Login and staying logged in

Your login system is built by you. No Firebase, no Google sign-in. That's exactly what the checklist asks for.

Think of a cinema
  • The access token is today's movie ticket. You show it at every door. It's quick to check, but it's only valid for 15 minutes.
  • The refresh token is your membership card, kept safely in your wallet. When the ticket expires, you show the card at the counter and get a new ticket. It lasts 30 days.
  • The cinema writes membership cards in its record book (the database), so it can cancel one (logout). It can't cancel a ticket, which is why tickets expire quickly.

Signing up

  1. On the Register screen you type name, phone and password. The screen calls authApi.register().
  2. The server scrambles the password with bcrypt (it can't be unscrambled), then inside one transaction saves: the user, their PASSENGER role, their passenger profile, an optional referral, and a 6-digit code (OTP). A trigger automatically creates their wallet with 0 taka.server/src/services/auth.service.js:70
  3. If any of those saves fails (for example, the phone number is already taken), ROLLBACK undoes all of them. There's never a half-created account.
  4. The code is sent by SMS. You type it on the OTP screen. The server checks it's correct, not expired, and not guessed too many times, then marks your phone as verified.
  5. The server creates a session row and a refresh token (saved together in a transaction), and sends back the access token plus the cookie. You're in.

Why you stay logged in after refreshing the page

Refreshing the page wipes JavaScript memory, so the access token is gone. Here is what happens next, automatically:

  1. The app starts and asks GET /me ("who am I?") with no token. client/src/context/AuthContext.tsx:29
  2. The server answers 401.
  3. The shared messenger in client.ts sees the 401 and calls POST /auth/refresh. The browser attaches the cookie by itself. client/src/api/client.ts:63
  4. The server finds the card's record and locks it (FOR UPDATE), cancels the old card, issues a new one, and gives a new ticket. This swap is called token rotation. server/src/services/auth.service.js:205
  5. The messenger repeats the original /me request with the new ticket. You never noticed anything.
  6. If the refresh fails too, you're sent to the welcome page.
Stolen card detection

If someone uses an old, already-swapped refresh token, the server assumes it was stolen. It cancels the whole session and answers REFRESH_REUSED, so both the thief and the real user must log in again.

Live updates

Letters vs a phone call

Normal HTTP is like sending letters: the browser writes, the server replies, done. The server can never write first. When a passenger books, the driver's phone must ring right now. So the app also keeps a phone line open using Socket.IO. Either side can speak at any time.

The wallet is a bank statement

Think of a bank

A bank never rubs out a line on your statement. Every deposit and withdrawal is a new line, and the balance is the running total. Your wallet_transactions table works exactly like that, and the database forbids editing or deleting its lines.

  • wallets: one row per user holding the current balance. A trigger creates it at sign-up.
  • wallet_transactions: one line per money movement (credit = in, debit = out).
  • The app never changes the balance directly. It adds a line, and the trigger trg_apply_wallet_txn updates the balance by itself (chapter 11).
  • Each line has a unique idempotency_key, like trip-payment-42. If a request is accidentally sent twice, the second one is refused, so nobody pays twice.

How to read any SELECT

You write a SELECT top to bottom, but the database runs it in this order. Read queries in this order and they make sense:

  1. FROM / JOIN: which tables, and how their rows match up
  2. WHERE: throw away rows you don't want
  3. GROUP BY: put the remaining rows into piles (one pile per driver, per month…)
  4. HAVING: throw away whole piles (like "fewer than 2 trips")
  5. SELECT: for each pile, calculate COUNT, SUM, AVG…
  6. ORDER BY: sort the answers
  7. FETCH FIRST n ROWS ONLY: keep only the top n

The big picture

What happens when I tap "Log in"?

LoginPage calls login() → POST /auth/login → rate limiter → validation → the service finds the user by phone and checks the password with bcrypt → in a transaction, saves a session and a refresh token → sends back an access token and a cookie → the screen asks /me → goes to the right home page for my role.

Why split code into routes, controllers, services and repositories?

Each layer has one job: routes choose which code runs, controllers handle the web request, services hold the rules, repositories hold the SQL. It's easy to find, test and change each one.

What is a middleware?

A function that runs before the main handler. It can check or change the request, or stop it. Examples: auth, validate, the rate limiters.

Where is the SQL for booking a ride?

insertRequest in server/src/repositories/rides.repository.js. All SQL lives in the repositories folder.

Login

How are passwords stored?

Only as a bcrypt hash (cost 12). It can't be turned back into the password. At login we hash what was typed and compare.

Why two tokens?

The access token (15 min) is fast to check but can't be cancelled, so it's short-lived. The refresh token (30 days) is recorded in the database, so logout can cancel it.

Why is the refresh token in an httpOnly cookie?

JavaScript can't read httpOnly cookies, so if a bad script ever ran on the page, it couldn't steal the token.

Could a passenger call an admin API with Postman?

No. Every admin route has auth and requireRole('ADMIN'), so the server answers 403.

How do I stay logged in after refreshing the page?

The first request gets a 401. The axios interceptor calls /auth/refresh with the cookie, gets a new access token, and repeats the original request.

Database

Explain one trigger.

trg_apply_wallet_txn: before a line is inserted into wallet_transactions, it locks the wallet, adds or subtracts the amount, stores the new balance on the line (balance_after) and updates wallets.balance. So the balance always matches the statement.

What's the difference between a function and a procedure?

A function returns a value and can be used inside SELECT, like fn_current_pricing. A procedure is run with CALL to do a multi-step job that changes tables, like sp_request_withdrawal. It hands values back through INOUT/OUT parameters.

Why did you make the withdrawal a procedure?

It's a multi-step workflow on several tables: lock and check the wallet, insert the withdrawal, insert the ledger debit (which updates the balance by trigger). Keeping it in one procedure means the steps always run together and in the right order.

What happens if completing a trip fails halfway?

ROLLBACK. There's no half-completed trip, no earning without payment and no wallet change. The error goes to the screen.

Two drivers accept at the same moment. What happens?

Both run SELECT … FOR UPDATE on the ride request. The second waits. The first marks it matched and commits. The second then sees status is no longer searching and gets 409 ALREADY_TAKEN.

What is $1 in your SQL?

A placeholder. Values are sent separately from the SQL text, which prevents SQL injection.

What is a view, and where do you use one?

A saved SELECT. v_driver_daily_earnings groups earnings per driver per day for the Earnings screen. v_city_monthly_revenue feeds the admin dashboard.

What does chk_fare_identity do?

It's a CHECK rule on trips: base + distance + time + waiting + surge + booking fee − discount must equal the total, or the database refuses the row.

Screens

What is useEffect for?

Running something after the screen draws, like loading data, starting a timer or listening for live messages, with a cleanup when the screen closes or the inputs change.

How does the passenger's screen know a driver accepted?

The live message trip:status with status assigned arrives instantly. As a backup, the screen also re-asks the server every 3 seconds.

How does the car move on the passenger's map?

The driver's phone sends location:update. The server saves it (in a transaction) and forwards it to the trip's room. The passenger's useRideTracking hook stores it in state, and React redraws the map.

What is ProtectedRoute?

A screen guard: not logged in → welcome page; wrong role → your own home. It's for convenience. The real security is on the server.

Your own rules

How are drivers chosen for a ride?

SQL finds drivers who are online, have GPS, drive the right vehicle type, are active, and haven't been offered this ride yet. JavaScript keeps those within 5 km, nearest first. Every 5 seconds the re-dispatch job widens the circle to the next drivers.

What if no driver accepts?

Each offer times out after 15 seconds and the next round goes out. After 5 minutes the expire job marks the request expired and the passenger is told to try again.

Can a driver end a trip early without the rider agreeing?

No. Away from the drop-off, "End trip here" is refused with EARLY_STOP_NOT_REQUESTED unless the rider tapped "Stop here" first. The server stores that time in trips.early_stop_requested_at, so there's proof of who asked.

How is the top-drivers list calculated?

One SELECT over completed trips joined with users, driver profiles and earnings. GROUP BY the driver, COUNT(*) for trips, SUM for earnings, ORDER BY trips then earnings, FETCH FIRST 10 ROWS ONLY. The rank number is the row's position.

What is the difference between WHERE and HAVING?

WHERE removes single rows before grouping. HAVING removes whole groups after grouping. In the top-rated report, WHERE t.status = 'completed' drops unfinished trips, and HAVING COUNT(t.id) >= $1 drops drivers with too few trips.

What does NOT EXISTS do in the inactive drivers report?

It keeps a driver only when the inner query finds no completed trip for that driver in the last 30 days. The inner query uses the outer driver's id, so it runs once per driver (a correlated subquery).

Why is u.full_name in GROUP BY?

Every column in SELECT that isn't inside COUNT, SUM or AVG must be in GROUP BY. Oracle requires it, and we follow the same rule.

Cash trip: how does the company get its commission?

The driver keeps the cash, so the app writes a debit of the commission on the driver's wallet. For wallet or online payments it's the opposite: the app credits the driver's share.
